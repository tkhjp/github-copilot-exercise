1. VS Code の、どの機能か

チャットの Permissions メニューにある「Sandboxing for terminal」が、今回紹介する機能です。 Copilot が実行するシェルコマンドに、利用できるファイル・通信先などの制限をかけます。VS Code 自体の Electron プロセス用 Sandbox や、Windows Sandbox の紹介ではありません。S1S2

開く場所と、設定後に変わること

見る場所 実際の操作・表示 意味
チャット入力欄の実行方式選択 Copilot を選択 本文の設定が適用される実行方式を確認する
Permissions メニュー Sandboxing for terminal をON 現在のセッションで、対応するコマンド・プロセスを制限する
VS Code の設定 chat.agent.sandbox.enabled を "on" 実行ホストで、新規セッションのSandbox既定値を設定する
チャット入力欄 /sandbox policy を実行 有効な制限を sandbox-policy.md で確認する

入口・適用範囲：S1S2。Copilot harness は「Copilot の実行方式」、Agent Host はそのセッションのコマンドやツールを動かすプロセスを指します。

同じコマンドでも、ON/OFFで変わるのは「アクセスできる範囲」

例：Copilot が開発スクリプトを実行 Sandbox OFF Sandbox ON ＋ 対応する制限を設定
作業フォルダーに成果物を書く OS・通常の権限に従う 許可された作業領域に出力できる
参照専用にしたフォルダーを書き換える Sandboxによる追加制限はない 対象のシェル処理からの書き込みを制限する
拒否対象のフォルダーを読む Sandboxによる追加制限はない 対象のシェル処理からのアクセスを制限する
不要な外部通信を行う Sandboxによる追加制限はない 設定した通信制限が適用される

設定例を用いた説明です。 ONにするだけで、この表のすべてが自動設定されるわけではありません。現在の既定値では外向き通信は許可されています。また、実行前のApprovalは別に判定されます。S1S3

2. 何ができるか：VS Code の実装と設定項目

機能一覧

機能 VS Code で指定する項目 設定すると何ができるか
ファイルアクセスの分離 chat.agent.sandbox.fileSystem.userConfiguredPaths パスごとに「読み書き」「読み取りのみ」「アクセス禁止」を指定する
ネットワークの制限 chat.agent.sandbox.network.* 外向き通信、ローカルネットワーク、許可・拒否する接続先を指定する

Sandbox外実行の制御 chat.agent.sandbox.allowUnsandboxedCommands 制限外での実行を確認付きで認めるか、要求自体を認めないかを選ぶ
セッション操作・状態確認 Sandboxing for terminal、/sandbox policy 今の会話だけON/OFFし、実際に適用中の制限を調べる

3行目の設定名は chat.agent.sandbox. 以降を省略表示。完全な名前・値は第3章と附録Bに掲載。S1S4

対象になる処理・ならない処理

処理 このSandboxとの関係
Copilotの標準シェルと、それが起動するスクリプト・子プロセス 対象
Agent Hostが起動・管理するローカルMCP／言語サーバー 対応設定がONなら対象。両設定の既定値は true
組み込みのRead／Edit／Writeなど、OSプロセスを起動しないツール 同じプロセスSandboxの対象外。別の権限チェックを使う

ユーザーが通常のターミナルへ手入力する任意のコマンド VS Codeの全ターミナルを一括でSandbox化する設定ではない

適用対象：S1S5。たとえば readonlyPaths にフォルダーを追加しても、別経路の編集ツールまで同時に読み取り専用になるとは限りません。

3. どう使うか：画面操作 → JSON → 実効確認

3.1 有効化する

手順 VS Code で行う操作 確認ポイント
1. 実行先を確認 チャットの実行方式を Copilot にし、ローカル／リモートの実行先を確認 本文はCopilot harnessの標準ツール向け。Localとは混用しない
2. 設定を開く Windows／Linux：Ctrl+,、macOS：⌘,。検索欄に @id:chat.agent.sandbox.enabled 値を on にする。リモート実行では接続先ホストの設定・OS条件を確認
3. 新規セッションを開始 新しいCopilotセッションを開く 既存セッションだけ変えるなら Permissions → Sandboxing for terminal
4. 有効な制限を確認 チャットに /sandbox policy と入力して送信 エディターで開く sandbox-policy.md を確認。設定変更後は再実行

設定エディター操作：S6。Sandboxの手順・適用先：S1。機能の利用条件は第5章を参照。

JSONで設定する入口： コマンドパレット（Windows／Linux：Ctrl+Shift+P、macOS：⇧⌘P）から Preferences: Open User Settings (JSON) を開き、既存の設定オブジェクトに以下のキーを追加します。ファイル全体を置き換えないでください。S6

設定例 · settings.json に統合
{
  "chat.agent.sandbox.enabled": "on"
}

"on" は文字列です。true ではありません。既定値は "off"。S1

変更方法 適用先 新しい会話の既定値も変えるか
実行ホストの chat.agent.sandbox.enabled そのホストで解決される設定 変える。新規セッションで確認する
会話の Sandboxing for terminal 現在のセッション 変えない。User／Workspace設定も書き換えない

リモートのセッションでは、設定パスもOS依存もコマンドが動くリモートマシン側のものです。組織管理の制限がある場合、会話の切り替えより優先されます。S1

3.2 ファイル：参照用・出力用・禁止領域を分ける

例：Windows上で、共通資料は参照のみ、成果物は別フォルダーへ出力、ダミー機密フォルダーはアクセス禁止にする。 以下のパスは説明用です。実在する必要なパスへ置き換えます。

設定例 · settings.json に統合
{
  "chat.agent.sandbox.enabled": "on",
  "chat.agent.sandbox.fileSystem.userConfiguredPaths": {
    "readwritePaths": ["C:\\sandbox-demo-output"],
    "readonlyPaths": ["C:\\sandbox-demo-reference"],
    "deniedPaths": ["C:\\sandbox-demo-private"]
  }
}
キー 上の例での効果 実際に確認すること
readwritePaths 出力先を読み書きできる シェルからファイルを作成できるか
readonlyPaths 参照フォルダーを読めるが書けない 読み取りは成功し、書き込みは拒否されるか
deniedPaths 指定フォルダーへアクセスできない 中のダミーファイルをシェルから読めないか

同じパスが重複指定された場合の優先順位は denied → readonly → readwrite。現在の作業ディレクトリには既定で読み書きが許可されます。空のリストは「その種類のアクセスが全くない」という意味ではありません。自動付与も含め、/sandbox policy で確認します。S1

macOS／Linuxの場合： キーは共通で、配列のパスだけを /Users/... や /home/... など実行ホストのパスに置き換えます。古い fileSystem.mac / fileSystem.linux の例は本文のCopilot標準ツールには使いません。S1

3.3 ネットワーク：通信を止める／必要な接続先に絞る

やりたいこと 主な設定 結果
シェルの処理を外向き通信なしで動かす network.allowNetwork: false 対象処理の外向き通信を止める
必要なAPIなどに絞って通信させる network.allowNetwork: true ＋ network.allowedDomains 外向き通信を許可しつつ、接続先を制限する
ローカル開発サーバー等への接続が必要 network.allowLocalNetwork を検討 ローカルネットワークアクセスの可否を別に調整する

表のキーは chat.agent.sandbox. 以降を表示。Copilotとモデルの通信まで止めて、オフラインAIとして使える機能ではありません。 ここで扱うのはSandbox対象処理の通信制限です。S1S5

例A：外向き通信を止める

設定例 · settings.json に統合
{
  "chat.agent.sandbox.enabled": "on",
  "chat.agent.sandbox.network.allowNetwork": false,
  "chat.agent.sandbox.network.allowLocalNetwork": false,
  "chat.agent.sandbox.credentials.authenticategit": false,
  "chat.agent.sandbox.credentials.authenticategh": false,
  "chat.agent.sandbox.allowUnsandboxedCommands": false
}

依存関係が導入済みのテストなどを想定した設定例です。認証が不要なため連携をOFFにし、Sandbox外への切り替えも許可しません。企業のプロキシ等が別に適用されるWindows環境では、この例のまま起動できない場合があります。次のWindows注意点を確認してください。S1

例B：接続先を api.github.com に絞る（macOS／Linuxの例）

設定例 · settings.json に統合
{
  "chat.agent.sandbox.enabled": "on",
  "chat.agent.sandbox.network.allowNetwork": true,
  "chat.agent.sandbox.network.allowedDomains": ["api.github.com"],
  "chat.agent.sandbox.network.deniedDomains": [],
  "chat.agent.sandbox.network.allowLocalNetwork": false
}

API接続先の例であり、Git操作や依存パッケージ取得がすべて動く構成ではありません。必要なリダイレクト先・配布先・社内サービスは別途確認します。許可した接続先への「読み取り専用」を保証する設定ではなく、API更新なども可能になり得ます。S1S7

Windows固有の注意： 公式ガイドでは、プロキシ・ホスト名制限・認証情報マスキングを使う構成は chat.agent.sandbox.network.allowLocalNetwork: true が必要です。ローカルリスナーに到達できないとコマンドが起動しません。例BをWindowsへ移す場合はこの変更と、その結果広がるローカルネットワークアクセスを確認します。「動かすためだけにON」とはしません。S1

3.4 認証・開発ツール・MCP／言語サーバー

以下は、Sandbox本体がONのときに検討する設定です。 表の設定名にはすべて chat.agent.sandbox. が付きます。S1S4

設定名（接頭辞省略） 既定値 false にした場合
fileSystem.allowDevToolAccess true 開発ツール設定・キャッシュ等への自動付与を外す。ビルドや依存復元が失敗する場合は必要なパスを個別に追加
credentials.authenticategit true Sandbox内Git HTTPS操作向けの認証連携を外す
credentials.authenticategh true Sandbox内のGitHub CLI（gh）向けの認証連携を外す
mcpServers true 管理下MCPサーバーに対するこのSandbox適用を外す。MCPを禁止する設定ではない
lspServers true 管理下言語サーバーに対するこのSandbox適用を外す。言語サーバーを禁止する設定ではない

開発ツール向けの自動アクセスには、レジストリトークンを含む設定や共有キャッシュが含まれ得ます。Git／gh連携をOFFにしても、許可された別ファイルや環境経由の認証情報を一括で消すわけではありません。S1S5

3.5 制限に阻まれたとき、Sandbox外実行を認めるか

設定例 · settings.json に統合
{
  "chat.agent.sandbox.allowUnsandboxedCommands": false
}
値 VS Codeでの挙動 注意
true（既定） 必要に応じて Allow Outside Sandbox の承認を要求できる 承認した操作にはSandboxのファイル・通信制限が適用されなくなる
false Sandbox外実行の選択肢を出さず、その要求を失敗させる 承認を省略して無制限に実行する設定ではない

会話全体の例外を承認すると、その後のコマンドも再度ONにするまで制限外で実行され得ます。失敗時は、まず必要なパス・通信先を確認します。S1

3.6 /sandbox policy で「本当に効いている設定」を見る

このコマンドはCopilot harness用です。入力するとMarkdownプレビューが開き、実行ホスト、ON/OFF、OSの実装、ファイル・通信の実効ポリシーを確認できます。モデルの応答を生成させるプロンプトではなく、設定も変更しません。変更後はもう一度実行して更新します。S1

確認する観点： 設定ファイルに書いた値だけでなく、作業ディレクトリ・開発ツールの自動付与や組織管理の制限が加わった結果を見ます。設定の不一致を調べる際も、このレポートを起点にします。

4. 活用例：長時間の開発タスクで、承認待ちを減らす

4.1 何と何を組み合わせるか

会社でAllow allを使えない場合でも、会社が個別の自動承認を認めていれば、Manual permissionsのまま、定型コマンドの事前許可とSandboxを組み合わせる使い方を検討できます。S3S7

制御 この例での担当 設定・操作
Sandbox コマンドがアクセスできるファイル・通信先を制限 第3章のSandbox設定
Terminal Approval 確認済みのテスト・Lint・ビルドの逐次確認を減らす chat.tools.terminal.autoApprove
組織管理 自動化してはいけない操作の確認・禁止を維持 適用中の企業ポリシー。利用者の設定では緩和できない

現行Copilot harnessでは、Sandbox ONだけで全シェル承認が消えるとは説明しません。 公式の現行仕様はSandboxとApprovalを別の制御として扱っています。S1S3

4.2 VS Code の設定例

前提は、会社がTerminalの個別自動承認を許可していることと、実行するリポジトリのスクリプト内容を確認済みであることです。Permissionsでは Manual permissions を維持します。現行ガイドではWorktreeセッションはAllow allになるため、この例では Folder isolation のセッションで確認します。S3

以下は第3章のファイル・通信設定へ追加する設定例です。

設定例 · settings.json に統合
{
  "chat.agent.sandbox.enabled": "on",
  "chat.agent.sandbox.allowUnsandboxedCommands": false,
  "chat.tools.terminal.autoApprove": {
    "/^npm (test|run lint|run build)$/": true,
    "/^git push(?:\\s|$)/": false
  }
}
コマンド・状態 この設定例で意図する扱い
npm test / npm run lint / npm run build 追加した許可ルールの対象。Sandboxの制限は残る
npm test -- --watch など、文字列が異なるコマンド この追加ルールの対象外。他の既定・承認設定によって判定される
git push false ルールにより自動承認せず確認する。企業のdenyがあれば禁止
許可されたコマンドが拒否対象パスにアクセス 自動承認の対象でも、Sandbox側でそのアクセスを制限
Sandbox外での実行を要求 この例では例外を許可しない

autoApprove の false は「実行禁止」ではなく「確認が必要」です。 複合コマンドは原則サブコマンドごとに判定され、すべてが許可に一致し、手動承認（false）ルールに一致しない場合に自動承認されます。chat.tools.terminal.enableAutoApprove が無効なら自動承認は使えません。S3

npm test などの名称だけでは安全性を判断できません。内部のスクリプトや依存関係は別の操作を行えます。承認ルールは利便性のための仕組みであり、強固な隔離そのものではありません。S3S5

4.3 期待する変化と、残る確認

導入前の作業例 設定後に目指す作業例
テスト → 確認待ち → Lint → 確認待ち → ビルド 事前許可した定型コマンドは継続し、未許可の操作で確認する
人が毎回コマンドを見て判断 実行範囲はSandboxで制限し、承認対象の操作を人が判断

上表は活用イメージであり、実測結果ではありません。削減される回数は既存のルールと実行コマンド次第です。企業の permissions.ask はその都度の人間の承認を要求し、permissions.deny は実行を禁止します。単にAllow allが禁止されている場合と、各コマンドへの逐次承認が必須の場合は区別します。S7

4.4 Local harness の説明を、そのまま当てはめない

実行方式 Sandboxと承認についての説明
Copilot harness（本文） アクセス制限とApprovalを分けて設定する。/sandbox policy で確認可能
Local harness chat.agent.sandbox.allowAutoApprove がTerminal承認動作を制御する。本文のCopilot Sandboxを設定するキーではない

初期の1.109資料には、Sandbox内コマンドの標準確認を省略する説明があります。それを根拠に、現行Copilotのすべての実行方式で同じ動作とみなさないことが重要です。S1S8

ほかの活用例

資料のシェル処理： 入力資料のパスを読み取り専用にし、生成結果のフォルダーだけ書き込み可能にする。ローカルMCPの利用： Agent Host管理下のサーバーに、必要なパス・接続先を限定して渡す。どちらも対象外の編集ツールや、許可した接続先での副作用には別の制御が必要です。S1S5

5. 制約・利用条件：どこまで任せられるか

OSと実行場所の条件

コマンドの実行先 公式文書の状態 前提・注意点
macOS Preview Sandboxガイド上、追加依存の導入は不要
Linux / WSL2 Preview bubblewrap と socat が必要。WSL1は非対応
Windows Experimental 対象Windowsのセキュリティ更新が必要。プロキシ等の構成にも条件あり

状態表記：S3。前提条件：S1。VS Code本体のStableと、Sandboxの各OSでの機能ステータスは別です。

Windowsについて、公式ガイドは2026年9月8日の更新として、Windows 11 24H2／25H2では KB5124008、26H1では KB5124012 を挙げています。会社の配布状況と適用対象を管理部門で確認してください。リモート実行時は、接続元のPCではなく実行ホストの条件を確認します。S1

できないこと・誤解しやすいこと

期待してはいけないこと 実際の制約・必要な対応
VS Code全体や、全ツールの一括隔離 Read／Edit／Write等は別の権限チェック。手入力の全Terminalまで自動で対象になる設定ではない
ONだけで完全に閉じた実行環境になる 外向き通信、開発ツールアクセス、Git／gh連携、Sandbox外実行要求は既定で許可。必要なものを個別に調整
許可された場所では事故が起きない 読み書き可能なファイルの誤変更や、許可APIへの更新は起こり得る。差分レビューを残す
企業が必須にしたApprovalを消す 強制ask／denyは維持。管理ポリシーの回避策ではない
VMや別アカウント相当の完全分離 実行ホストのユーザーアカウント上で動作。単独の安全境界でも端末セキュリティの代替でもない
長時間タスクの無人完了を保証 追加質問、依存不足、認証、エラー、利用上限などはSandboxとは別の問題

対象範囲・既定値：S1。安全上の範囲：S5。強制承認：S7。長時間タスクの完成率・待ち時間削減は社内環境で未測定です。

MCPも二種類を区別： chat.agent.sandbox.mcpServers はCopilot Agent Host管理下のプロセス向けです。mcp.json の sandboxEnabled で指定する per-server MCP sandboxing は別機能で、公式資料ではmacOS／Linux対応、Windows非対応とされています。S1S9

附録A. 最近の変更：何が、どう違うのか開く

A.1 1.141で説明されているポイント

1.141は2026年10月7日公開です。Sandbox自体の初登場ではありません。以下の「1.141掲載」は、そのリリースノートで紹介された内容を意味し、すべてが1.140からの新規追加であることを意味しません。S2S8

項目 区分 具体的な内容・影響
Windows／macOS／Linux 1.141掲載 クロスプラットフォームのCopilot Agent Host Sandboxを紹介。WindowsはOS更新要件を伴う
ローカル・リモートのセッション 1.141掲載 コマンドが動くマシン側で制限。ファイルパスもそのマシンを指す
会話のSandbox切り替え 1.141掲載 Permissions内の Sandboxing for terminal から操作
ローカルMCP／言語サーバー 1.141掲載 Sandbox有効時、対応する管理下サーバーにも既定で適用
ChatAgentSandboxEnabled の扱い 1.141で明記された変更 Agent Hostでは強制要件ではなく、上書き可能な既定値へ。Localの動作は変更なし
企業がSandboxを必須にする方法 1.141の移行案内 統一管理設定の sandbox.enabled: true と sandbox.allowBypass: false を利用する

根拠：S2。管理側のJSONはVS Codeの個人用 settings.json とは別物です。

附録B. 設定項目早見表開く

Copilot harness・標準ツール向け。 「既定」はユーザー・組織側の上書きがない場合です。実効値はセッションで確認します。S1S4

完全な設定名 値・既定 役割
chat.agent.sandbox.enabled "off" / "on"、既定 "off" 本体のON/OFF
chat.agent.sandbox.fileSystem.userConfiguredPaths オブジェクト、各配列は空 readwritePaths / readonlyPaths / deniedPaths
chat.agent.sandbox.fileSystem.allowDevToolAccess Boolean、既定 true 開発ツール設定・キャッシュ等への自動アクセス
chat.agent.sandbox.network.allowNetwork Boolean、既定 true 外向き通信
chat.agent.sandbox.network.allowLocalNetwork Boolean、既定 false ローカルネットワーク
chat.agent.sandbox.network.allowedDomains 配列、既定 [] 許可する通信先
chat.agent.sandbox.network.deniedDomains 配列、既定 [] 拒否する通信先
chat.agent.sandbox.credentials.authenticategit Boolean、既定 true Git HTTPS認証連携
chat.agent.sandbox.credentials.authenticategh Boolean、既定 true GitHub CLI認証連携
chat.agent.sandbox.mcpServers Boolean、既定 true 管理下ローカルMCPのSandbox適用
chat.agent.sandbox.lspServers Boolean、既定 true 管理下言語サーバーのSandbox適用
chat.agent.sandbox.allowUnsandboxedCommands Boolean、既定 true Sandbox外実行の承認要求

承認側の関連設定は別グループです：chat.tools.terminal.autoApprove（コマンドルール）、chat.tools.terminal.enableAutoApprove（自動承認の可否）、chat.tools.eligibleForAutoApproval（ツール別の確認要否）。組織の制約を変えずに利用可能な範囲を確認します。S3

附録C. チームで試すときの確認手順開く

以下は未実施の検証手順案です。実データ・本番API・本物の秘密情報を使わず、使い捨てのリポジトリとダミーファイルで実施します。

確認 実施内容 観察する結果
1. 実行方式・状態 Copilot / Manual permissions / Folder isolationを確認し、/sandbox policy を保存 正しい実行先でSandboxがONか
2. 参照専用パス 第3章の設定後、シェル経由でダミーファイルを読み取り、その後書き込みを試す 読み取りは成功、書き込みは拒否されるか
3. 拒否パス シェル経由で禁止フォルダーのダミーファイルを読む アクセスが拒否されるか
4. 通信 通信OFF／接続先限定の構成を別々に確認 必要な接続だけ成功し、許可していない通信は制限されるか
5. 定型処理 同じリポジトリ・同じタスクでテスト／Lint／ビルドを実行 承認ルールに一致する操作の確認回数が減るか
6. 制限外要求 allowUnsandboxedCommands: false で範囲外実行を要求させる 例外として実行されないか

二段階で比較すると原因を切り分けやすくなります。 まずSandboxをONのまま、Terminal事前許可の追加前後を比較して承認削減を確認します。次に同じ承認ルールで、SandboxのON/OFFによるダミー領域へのアクセス差を確認します。実行方式・OS・組織ポリシーは固定します。

記録する項目は、VS Codeバージョン、実行ホスト、実行方式、適用設定、コマンド、確認回数、待ち時間、拒否されたアクセス、タスク完了の可否です。「自動で進んだ」だけでなく、「制限対象にはアクセスできなかった」ことも確認します。

公式資料・調査範囲開く

本資料は公開仕様の調査です。設定例は本資料用に作成し、JSON構文を検査しました。機能の稼働、OSごとの拒否動作、企業ポリシーの適用、承認削減量は社内端末で未検証です。本文は現行製品の操作・設定を先に示し、初期の仕様やLocal互換動作を混在させない構成です。
